## Purpose

Let people select multiple filesystem scopes and receive predictable file eligibility even when filesystem notifications are incomplete or folders become unavailable.

## ADDED Requirements

### Requirement: Explicit scope enrollment
The app SHALL let the user add, configure, enable, pause, reconnect and remove multiple folder scopes without deleting their contents. New scopes SHALL begin disabled and baseline indexing SHALL NOT execute rules on existing files. Duplicate and overlapping watch roots SHALL be rejected.

#### Scenario: Enroll existing folder
- **WHEN** the user adds a folder containing existing files
- **THEN** the app stores the folder disabled and indexes a baseline without applying actions

#### Scenario: Remove configuration
- **WHEN** a watched folder is removed
- **THEN** its files and historical operation evidence remain and new scheduling for that scope stops

#### Scenario: Overlapping scope
- **WHEN** a user selects a root that contains or is contained by an existing watched root
- **THEN** the app rejects enrollment with an explanation

### Requirement: Defined file eligibility
The app SHALL support recursion, hidden-file inclusion, relative-path exclusions and native/polling modes with the defaults and ranges in the user option catalog. Only regular files SHALL be action targets. Packages, symlinks, Finder aliases, app data, staging and Trash SHALL be excluded.

#### Scenario: Default recursion
- **WHEN** a file arrives only in a nested subfolder and recursion is off
- **THEN** it is not eligible under that root

#### Scenario: Symlink escape
- **WHEN** a directory symlink points outside the selected scope
- **THEN** the app neither traverses the link nor processes its referent as a scope member

### Requirement: Stability and local availability
The app SHALL defer active/incomplete files until the size and modification time remain unchanged across observations at least two seconds apart, revalidate before effects, and explicitly defer files unstable for five minutes. The app SHALL NOT intentionally hydrate cloud placeholders.

#### Scenario: Ongoing download
- **WHEN** a file continues growing or has a default excluded partial-download extension
- **THEN** rules do not modify it and the app reports a pending or excluded state

#### Scenario: Nonlocal placeholder
- **WHEN** file contents are not locally available
- **THEN** processing is skipped or deferred with a reason and no download is requested

### Requirement: Event recovery and scheduling
The app SHALL monitor before scanning, reconcile missed/coalesced events and changed files on launch/wake/resume, provide polling fallback with its reliability limits, and evaluate time conditions when deadlines become due while awake. New unchanged historical files SHALL require Run Now rather than implicit initial execution.

#### Scenario: Event overflow
- **WHEN** filesystem events or the work queue overflow
- **THEN** the affected scope is reconciled rather than silently losing final-state eligibility

#### Scenario: Age threshold while idle
- **WHEN** a stable file becomes old enough to satisfy an enabled age condition without a new filesystem event
- **THEN** it becomes eligible within the minute-resolution awake scheduler

### Requirement: Watch identity and availability
The app SHALL retain folder identity and configuration across restart and unavailable volumes. It SHALL pause uncertain or inaccessible roots and require reconnection/confirmation rather than applying rules to an unrelated object reusing a path.

#### Scenario: Reused mount path
- **WHEN** a different volume appears at a watched folder's old path
- **THEN** rules remain inactive for that scope until its identity is resolved

### Requirement: App output suppression
The app SHALL suppress automatic reprocessing of exact output versions generated by its own operations and undo across all watched scopes. Later external modifications and explicit Run Now SHALL remain eligible.

#### Scenario: Output in another watched folder
- **WHEN** a copy or move creates an output in another watched root
- **THEN** that output version does not start a new automatic chain

#### Scenario: External edit after output
- **WHEN** the user externally changes an app-produced output
- **THEN** the new file version can be evaluated normally
